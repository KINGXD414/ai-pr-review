### 章节 3：数据说话 · 5×4 评测矩阵（4:00 ~ 6:30）

**画面**：
- [4:00] 切到 README 的「5×4 评测矩阵」段（或 `demo/v020_evaluation_matrix.md`）
- [4:10] 镜头停在全表，停留 5 秒让观众看清数据
- [4:20] 逐行指：先看 easy case——json-5187 和 spdlog-3541，四招全部 100%，说明简单 PR 没分歧
- [4:40] 指到 muduo-729（low）：baseline 90%，但 linus 和 critique 都跌到 70%，为什么？因为这是一个低风险重构，严苛策略反而误报
- [5:00] 指到 spdlog-3594（high）：baseline 62%，linus 爆到 92%，其他不变——只有 linus 在这个 case 上真正帮到忙
- [5:15] 切到 README「四条关键发现」列表，逐条念
- [5:45] 切到 `code/eval/comparison_report.md`，展示完整对比报告

**配音词（约 450 字 ≈ 150 秒）**：

> 接下来是数据。我们不只说"三招更好"，我们做了对照实验。
>
> 5 个真实开源 PR，4 种策略交叉打分，结果是这样的——
>
> 先看简单 case：json-5187 和 spdlog-3541，四招全是 100%，没有分歧。这种 PR 本来就没问题，怎么审都行。
>
> 有意思的在后面。muduo-729，标的是 low 难度，baseline 拿 90%，但 linus 和 critique 都掉到 70%。为什么？因为这是个低风险重构，严苛策略反而把正确代码标成了问题——误报。
>
> 再看 spdlog-3594，high 难度，baseline 只有 62%，linus 直接拉到 92%。其他两招没动。只有 linus 在这个 case 上真正帮了忙，consensus 投票反而把 linus 的正确判断给稀释了。
>
> 所以数据告诉我们四件事：
> 第一，简单 PR 无脑过，策略不影响结果；
> 第二，严苛不是万能的，低风险 PR 上反而误报更多；
> 第三，consensus 多数裁决不一定最优，可能稀释掉正确判断；
> 第四，平均分看 linus 最高 87%，但代价是低风险 case 的误报。
>
> 我们以为三招都会涨，结果数据告诉我们事实复杂得多。这不是坏事——这恰恰说明我们需要数据，而不是直觉。

**字幕板**：
- 章节标题：`数据说话 · 5×4 评测矩阵`
- 四条发现用白字逐条叠出：
  - `① 简单 PR 无分歧`
  - `② 严苛 ≠ 更好，低风险时误报↑`
  - `③ 多数裁决可能稀释正确判断`
  - `④ Linus 均分最高但代价是误报`

### 章节 4：工程化 · 诚实（6:30 ~ 9:00）

**画面**：
- [6:30] 切到 ADR 列表：`docs/adr/` 三个文件
- [6:40] 打开 `001-differentiation-strategy.md`，扫一眼决策结构和"选择"段

- [7:20] 切到 `.github/workflows/` 两个 yaml 文件，指一下双 workflow 结构
- [7:40] 切到 Release 页面，展示 `ai-pr-review-v0.2.0-linux-x64.tar.gz` + `.sha256`
- [8:00] 切到 `code/src/prompt/personas.h`，指三审制 prompt 模板
- [8:20] 切到 README「工程化基建」段，快速扫过

**配音词（约 450 字 ≈ 150 秒）**：

> 工程化这块，我们不追求炫技，但每个决策都写了下来。
>
> ADR 架构决策记录——三个文档，分别记录为什么选三审制、为什么用这套评测框架、为什么 rulehit 格式这样设计。不是"我们觉得好"，是"我们考虑了 A 和 B，选了 A，原因是……"。
>
> KODO 上传，零 SDK。没有 pip install qiniu，没有 npm 依赖，230 行 C++ 手写 HTTP + HMAC 签名，连上传 token 都是手算的。为什么？因为这是一个 C++ 项目，配套工具也必须是 C++。外部依赖越少，构建链越可控。
>
> GitHub Actions 双 workflow：一个是 CI——PR 触发自动编译和审查；一个是 Release——tag 触发自动打包、上传 Release Asset、生成 sha256 校验文件。
>
> 三审制的 prompt 模板在这里——personas.h，审查者、self-critique、consensus 三套 prompt，每个角色有明确的职责边界和输出格式。审查者给初评，self-critique 质疑初评，consensus 综合裁决。
>
> 诚实说局限：consensus 不总是最优，刚才数据已经展示了。三审制的耗时是单审的 3 倍，简单 PR 上没必要。这些我们在报告里都写了，不藏。

**字幕板**：
- 章节标题：`工程化 · 诚实`
- 关键数字叠出：
  - `KODO 上传：0 依赖 · 230 行 C++`
  - `GitHub Actions：双 workflow`
