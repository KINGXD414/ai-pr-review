# AI PR Review — 面试话术稿

> 目标岗位：AI 应用开发工程师（Agent / MCP / Skills 方向）
> 用法：**背 30 秒电梯介绍 + 每个小组的核心结论**，其余理解思路即可。
> 原则：**每个结论都要能指到代码里的具体位置或测试数据**。说不出数字的结论不要说。

| 项目 | 正确数字 |
|---|---|

## 1. 30 秒电梯介绍（背熟，一字不差）

> "这是一个 **C++17 写的 AI 代码审查工具**，输入 GitHub PR 链接，输出结构化 Markdown 审查报告。
> 架构上做了三层：**静态规则引擎**给确定性事实、**libclang AST 分析**给跨文件上下文、**LLM** 做综合判断。
> 但核心不是这三层，而是我把它改造成了真正的 **Agent**——给模型 6 个工具，由它自己决定先调什么、后调什么、调几次，形成 Function Calling 闭环；再配一套 **RAG**（默认 BM25，可切到向量余弦）给它喂团队规范和历史审查；最后把整个能力包成一个 **MCP server**，让 Claude Code / Cursor 能直接调用。
> 我还搭了评测框架做量化：5 条真实 PR、4 种配置跑矩阵，最佳配置把综合分从 baseline 的 82% 提到 **87%**，并且我有数据证明 **consensus 三次投票零增益却多花 3 倍开销**——所以我没用它。"

**说得出的亮点**：改造成了 Agent（不是套壳 prompt）、有量化评测、敢给出负面结论。

## 2. A 组：动机与整体架构

**Q：为什么要做这个？市面上不是有 CodeRabbit、Copilot Review 吗？**
> 三点差异定位：
> 1. **可控**：规则引擎的结果是我自己确定的，不依赖模型心情——这是压幻觉的地基。
> 2. **可嵌入**：它是 C++ 二进制 + CI workflow + MCP server，能塞进任何流水线；不是只能 browser 里点。
> 3. **可量化**：我写了评测框架，20 次真实 LLM 调用跑出 5×4 矩阵，每种配置的好坏有数字，不是"我觉得更好"。

**Q：为什么用 C++ 写？AI 应用不是都用 Python？**
> 这是技术选型问题，我当时的判断：项目要能**编译成单个二进制、跑在 CI 里、无运行时依赖**，同时又要用 libclang 做真实 AST 分析——libclang 的 C API 用 C++ 调用最自然。Python 侧的生态（LangChain 之类）在这场景帮不上忙，反而会引入版本地狱。
> 真正需要胶水的地方（MCP server）我用了纯 Python 标准库，因为那里重点是协议，不是性能。**该用 C++ 的地方用 C++，该用 Python 的地方用 Python**。

**Q：三层架构里，为什么必须先把规则引擎的结果喂给 LLM？**
> 这是我踩的最大的坑（可以自然接到 §7 踩坑故事）。核心逻辑：**LLM 擅长判断，不擅长精确枚举**。让它自己去 diff 里数"哪个 malloc 没配 free"，会漏、会编。规则引擎是确定性的枚举，命中就是命中，行号精确。把 RuleHit 列表喂进去，等于**给模型一份带行号的事实清单**，它只需要做归因和建议。
> 对应的幻觉治理：评测里专门有一维 `must_not_hallucinate`，占 30% 权重，专门罚"编造不存在的标识符"。

## 3. B 组：Function Calling / Agent（最核心，JD 直接考查）

**Q：你的 Agent 和普通 prompt 调用到底区别在哪？**
> 普通调用是**我编排**模型：fetch → 拼 prompt → 一次调用。工具选择、调用顺序、调用次数全是写死的。
> Agent 是**模型编排**工具：我把 6 个工具的 JSON Schema 发给模型，它每轮返回 `tool_calls`，我在本地执行并把结果以 `role: tool` 消息回灌，再让它继续。它会自己决定"这个 diff 有 malloc 我先跑规则引擎""这里涉及虚函数，我查一下 AST""这个文件在 test 目录，风险低"。
> 一句话：**workflow 是我画好的流程图，Agent 是我给它能力和上下文，它自己走。**

**Q：怎么保证它不会死循环？**
> 三重保险：
> 1. **有界循环**：`--agent-max-iter`，默认 6，硬上限 12，超了就取最后一份 `draft_comment` 的内容兜底，绝不无限自旋。
> 2. **终止条件明确**：模型返回不带 `tool_calls` 的纯文本，立即收敛。
> 3. **temperature 固定**，同一份输入行为可复现。
> 另外我写了 **mock 测试**证明这个循环正确（`agent_loop_tests`）：用假网关脚本化 5 轮响应——规则引擎 → list_skills → select_skill → rag_query → 终稿，断言 reports 非空、轮数正确。**不依赖网络、不依赖真实模型**，CI 里永远能跑。

**Q：工具调用失败了怎么办？**
> 工具返回字符串，包括错误语义的字符串（比如"`--source-dir` 未配置，AST 分析不可用"）。这些错误信息会**原样回灌给模型**，让模型自己决定降级策略——比如改用规则引擎的结果，或者直接基于 diff 判断。这比我在代码里写 try-catch 兜底更灵活：**把失败变成模型可见的信息，而不是异常**。

**Q：`tool_calls` 的具体协议？**
> OpenAI 兼容的 `tools` 协议：请求体带 `tools` 数组（每个含 `name`/`description`/`parameters` JSON Schema）；响应里 `choices[0].message.tool_calls[]` 每项有 `id`/`function.name`/`function.arguments`。执行后我按 `tool_call_id` 一一对应地回灌 `role: tool` 消息——**这个 id 必须对齐，否则模型会认不出哪个结果对应哪个调用**，这是实现里最容易错的一步。

## 4. C 组：RAG / Embedding / 向量库

**Q：为什么 RAG 默认走 BM25 而不是向量检索？**
> 三个理由：
> 1. **零依赖、断网可演示**——面试当场、CI 里、内网都能跑。向量路径要 embedding 模型或远端 API，等于引入密钥、网络、延迟三个故障点。
> 2. **确定性**——BM25 输出稳定可复现，便于测试；远端 embedding 每次结果可能漂移。
> 3. 在这个场景（几百到几千条规范条文），**BM25 的召回质量并不比小向量模型差**，而成本低几个数量级。
> 但我没把它锁死：`Retriever::search_best()` 是统一入口，检测到有 embedding 就走向量余弦，没有就自动回退 BM25。**默认走便宜稳的路，能力留在开关后面。**

**Q：那你的 embedding 是什么模型？**（⚠️ 这是弱项，必须诚实，见 §8）

**Q：向量库为什么自己写暴力余弦，不用 hnswlib / Milvus？**
> 语料量级是千级 chunk，暴力余弦 O(n) 在毫秒级完成，**正确性优先**。我把 `VectorStore` 抽成接口，`BruteForceStore` 只是它的一个实现；数据规模上来了，换一个 `HnswStore` 实现即可，**调用方零改动**。
> 这也是我想表达的工程态度：**先用一个能验证正确性的朴素实现打通端到端，把抽象边界立住，再按瓶颈替换实现**——而不是一上来就堆重型依赖。

**Q：向量索引为什么要落盘 JSON？**
> 为了把 RAG 生命周期做成**可复现的闭环**：`--embed --index xxx.json`，首次构建并保存，之后直接加载，跳过重新嵌入。这个文件是真实的产物（id + vector + text），不是缓存日志——你可以把它提交进仓库、分发给同事、在 CI 里复用。**"向量数据库"这个概念在我这里不是空话，是有实体文件的。**

**Q：语料从哪来？**
> 两部分：内置 8 条规则的知识描述 + `--rag-corpus-dir` 挂接团队自己的 `.md/.txt`。这样"团队约定"这类软规范（比如"异步回调里禁止 XXX"）也能进检索。

## 5. D 组：Skills / MCP

**Q：Skills 和 prompt 模板有什么区别？不就是换个说法包装吗？**
> 这个问题问得好，**如果只是包装那确实没价值**。我的设计约束是：**不重复任何一行 prompt 逻辑**。5 个 persona 和 2 个元策略都是已经跑过评测、有分数的现成资产（linus 87% / self-critique 80% / consensus 82%），Skill 注册表只给它们加三样东西：**id、自然语言描述、索引**。
> 加完之后产生的能力是之前没有的：**模型可以自己发现并选择策略**——Agent 里 `list_skills` 让它知道有哪些选项，`select_skill` 让它按 diff 特征选（比如看到 test 目录就用 zen 模式，看到内存操作就用 devil 模式）。**从"人配置策略"变成"模型选择策略"**，这是 Skill 的价值所在。

**Q：MCP 是什么？为什么需要它？**
> MCP 是模型调用外部能力的**标准协议**，解决的是 N 个客户端 × M 个工具的集成爆炸。以前每个 AI 编辑器都要给每个工具写插件，现在是统一协议。
> 我的实现是 `mcp/server.py`：**纯 Python 标准库**，stdio JSON-RPC 2.0，就 200 行。它做的事只有一件——**协议翻译**：把 JSON-RPC 请求翻译成对同一个 C++ 二进制的命令行调用。
> 关键设计：**server 不复制任何业务逻辑**，所有审查能力来自同一个 `ai-pr-review` 二进制。这样 CLI、CI、MCP 三条路径行为完全一致，不会出现"CLI 和 MCP 结果不同"的分叉。

**Q：怎么接到 Claude Code / Cursor？**
> 在客户端的 mcp.json 配一个 stdio server：`python3 mcp/server.py`，环境变量指到二进制路径和 API key。之后模型在对话里就能直接调 `review_pr`——**"代码审查"变成了它能力集里的一个原生动作**。这就是 Agent + MCP + Skill 三件套的落点。

## 6. E 组：C++ 工程实现

**Q：AST 分析怎么做的？**
> 用 libclang 的 **C API**（`clang_parseTranslationUnit` + `clang_visitChildren`），不是手撕语法。提取三类信息：类及其基类（判断继承/多态影响）、函数签名（判断 API 变更）、包含文件。
> 踩过的坑：libclang 需要编译期参数才能正确解析项目（`-std=c++17`、include 路径），我让它接受外部传入编译参数；另外 Windows / macOS 上 libclang 不在默认 PATH，CMake 里写了多版本探测（12~18）+ 用户可通过环境变量覆盖。

**Q：HTTP / HTTPS 怎么做的？为什么 httplib 锁 v0.14.3？**
> 用 cpp-httplib（header-only）+ OpenSSL。锁 v0.14.3 是因为 **v0.15+ 要求 OpenSSL ≥ 3.0，而 Ubuntu 20.04 是 1.1.1f**——为了兼容性区间最大化，我选了同时支持两者的最后一个版本。这种兼容性取舍我在 README 里写了注释，因为它是踩过才知道的。

**Q：LLM 调用的重试怎么设计？**
> 传输层重试（超时、连接失败）和**业务层重试**分开：前者有限次重试+退避；后者针对"LLM 返回了格式不对的东西"。每条路径都记录 `attempts`，最终报告里能看出这次审查花了多少次调用——**可观测性对于排查成本很重要**。

## 7. F 组：踩坑与失败经验（面试官最爱问，用 STAR 答）

**坑 1：README 吹"三层架构"，代码里根本没接规则引擎（最有价值的失败故事）**
> **S**：项目文档写着规则引擎 → AST → LLM 三层。
> **T**：我要在这个基础上加 RAG，需要先确认 RuleHit 怎么进 prompt。
> **A**：我去读 `main.cpp`，发现**它从来没 include 过 `rules/engine.h`**，规则引擎是个跑不到的孤岛。我没有直接照着文档假设接着写——**先对着实现验证文档的说法**，然后才把 `RuleEngine().run()` 接进主流程，并把 RuleHit 渲染成独立区块注入 prompt。这是交付里优先级最高的修复（P0）。
> **R**：现在规则引擎在主流程必然执行，幻觉治理从此有了确定性来源。
> **这个故事我想表达的是**：我习惯**对着实现验证文档，而不是假设文档是对的**——这是我在这个项目里最值钱的一次发现。
> （面试官追问"为何之前的人没发现"：因为规则引擎有独立单测，单测绿不代表被集成——**测试通过 ≠ 功能生效**，这也是我现在写集成级测试的动因。）

**坑 2：开发环境里 libclang / OpenSSL / 网络全不可用**
> **S**：我在受限环境里无法访问 libclang / OpenSSL / 网络。
> **A**：没有硬等环境，而是写 stub 头（nlohmann/json、spdlog、CLI、httplib、ast_analyzer）+ 本地编译器做**离线语法与逻辑验证**，先把 RAG、Agent 循环、MCP 协议的正确性验证完。
> **R**：后来在真实环境（WSL + libclang-14）一次性编译通过，7/7 测试全绿。
> **表达的点**：受限环境下不阻塞自己，但也**清楚 stub 验证的边界**——所以后面一定要在真实工具链上复跑一遍。

**坑 3：stub 的假实现让测试"假过"**
> 我最初的 JSON stub 里 `parse()` 永远返回空对象，导致向量库的 save/load 往返测试看起来通过了。发现后我把 stub 升级成一个**小而真实的 JSON 实现**（递归下降 parser + dump）。这个教训是：**测试环境如果和真实环境行为不一致，绿灯没有意义**。

**坑 4：负面结论比正面结论更值钱**
> consensus（三次投票取交集）听起来很合理，跑完矩阵发现：**综合分 82%，和 baseline 持平，成本却是 3 倍**。我没有偷偷删掉这组数据，而是把结论写进 README 并标注"零增益"。同理 self-critique 在低难度 case 上反而 -2%（过度校准）。
> **面试官会很欣赏有数据、敢认结论的人。**

## 8. G 组：⚠️ 诚实边界 —— 会被戳穿的弱项（必须提前想好）

> 面试最危险的不是有弱点，而是对弱点含糊其辞。**这些都是我主动承认并准备好答案的**，一旦被问到，直接说，然后接上"为什么这样设计"和"怎么演进"。

**① HashingEmbedder 不是真正的语义嵌入**
> 承认：**它是字符 n-gram 哈希 + L2 归一化，捕捉的是字面重叠，不是语义相似度**。所以我不会说"我有语义搜索"。
> 为什么这样做：**离线、确定性、零依赖、断网可跑**——我需要一个任何环境都能复现的完整端到端路径，并且用它**验证整套 VectorStore / 检索流水线的正确性**。如果一上来就用远端 API，这条链路的测试就永远依赖网络。
> 怎么演进：`Embedder` 是抽象接口，实现 `RemoteEmbedder`（如 bge-m3 / text-embedding-3）并替换注入即可，**调用方零改动**。这是刻意留的缝，不是没做。

**② BM25 对中文分词支持弱**
> 承认：当前分词按 ASCII 字母数字切，**CJK 被当分隔符处理**，所以中文语料的词法召回不好。
> 怎么补：这正是**语义路径存在的理由之一**——`HashingEmbedder` 按字符 n-gram 处理，对中文是有效的。换句话说，中文场景建议 `--rag --embed`。
> 完整方案：换 jieba 之类的中文分词器，或直接上中文 embedding 模型。

**③ 规则引擎是逐行 / 正则匹配，不是数据流分析**
> 承认：它**发现不了跨函数的所有权转移**（比如 A 函数 malloc、B 函数 free 这种），也不做别名分析。
> 定位说明：我不想把它做成 clang-tidy 的竞品。它的角色是**给 LLM 提供低成本、高确定性的证据**，同时也用于**软治理**（test 文件降噪、TODO 提示）。
> 边界清楚本身就是设计的一部分。

**④ 评测样本量小（5 cases）**
> 承认：**绝对分数的统计意义有限**，样本太小。
> 它的真实价值在两点：**相对对比**（同一批 case 上不同配置的排序是稳定的）和**回归护栏**（改代码后跑同一组 case，防止退化）。如果要发论文级别的结论，需要扩到几十上百条。

**⑤ 没有流式输出、单次调用是同步阻塞**
> 承认，这是已知短板，在项目的"未来扩展"里列着。**没有做的原因不是没想到，而是优先级排序**——在 CI / MCP 批处理场景，延迟不像交互式 IDE 那么敏感。

**⑥ consensus 三次投票是负面结论**
> 见 §7 坑 4。这是主动暴露的负面数据，不是弱点。

## 9. H 组：下一步演进（"如果让你继续做会做什么"）

1. **`RemoteEmbedder` + `HnswStore`**：填充抽象接口，验证"换实现不动调用方"的设计承诺，同时获得真语义能力
