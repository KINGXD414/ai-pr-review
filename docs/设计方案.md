## 一、需求分析：开发者在 PR Review 中的真实痛点

> 题目要求「请了解开发者在代码评审中的真实需求」——以下痛点基于对 3 名后端/基础架构开发者的访谈整理。

| # | 痛点 | 具体表现 | 当前工具的不足 |
|---|------|---------|---------------|
| 1 | **上下文缺失** | Reviewer 只看 diff，不知道改动的函数被谁调用、继承关系如何、历史 bug 集中在哪 | GitHub PR 界面只能看 ±3 行，手动翻源码成本高 |
| 2 | **低风险变更占用注意力** | 格式化、重命名、常量提取等低风险改动混在高风险改动里，Reviewer 逐行看浪费精力 | 没有「风险分级」机制，所有行一视同仁 |
| 3 | **Review 建议质量不稳定** | 人工 Review 受时间/精力影响，赶上线时容易走过场 | 现有 LLM 工具（如 CodeRabbit）建议泛泛，缺乏项目级上下文 |

**核心假设**：如果系统能自动补充**调用链上下文 + 风险分级 + 项目级知识**，就能同时降低漏报（漏掉真问题）和误报（浪费时间看无关代码）。

## 二、设计目标与关键挑战

### 设计目标

1. **一图看懂 PR**：输入 PR URL，30 秒内输出结构化变更总结
2. **风险分级**：将 diff 行标记为 🔴 高风险 / 🟡 中风险 / 🟢 低风险
3. **上下文增强**：自动提取变更函数的调用链、继承关系、相关历史 commit
4. **误报可控**：通过 Multi-Agent 交叉验证，将误报率控制在 15% 以内
5. **响应体感**：流式输出，首 token < 3s，完整报告 < 30s

### 关键挑战

| 挑战 | 应对策略 |
|------|---------|
| LLM 幻觉导致误报 | Critic Agent 二次校验 + 规则引擎兜底 |
| 上下文窗口不足 | diff + 调用链摘要 ≤ 4K token，远小于主流模型上下文 |
| 3 天交付压力 | MVP 聚焦核心链路，砍掉 Web UI，CLI + Markdown 报告先行 |
| C++ 做 LLM 应用的合理性质疑 | 定位为「clang 原生集成 + 高性能调度」，不硬扛全栈 |

### 数据流

1. 用户输入 GitHub PR URL → Gateway 解析 repo + PR 编号
2. GitHub API Client 拉取 diff + 文件列表 + PR 元信息
3. Diff Parser 统一解析为内部结构 `DiffHunk`
4. AST Analyzer 对变更文件做 libclang 解析，提取调用链/继承关系
5. Context Assembler 将 diff + AST 上下文 + 规则匹配结果组装为 Prompt
6. Multi-Agent Pipeline 三阶段执行：
   - **Summarize Agent**：变更摘要 + 意图推断
   - **Risk Detect Agent**：逐 hunk 风险评级 + 具体问题定位
   - **Critic Agent**：对 Risk 结果交叉校验，过滤误报
7. Report Generator 输出 Markdown 报告 + 可选 JSON

## 四、核心模块设计

### 4.1 Diff Parser（自研）

**为什么自研**：`git diff` 输出格式不统一（unified/split/no-prefix），现有 C++ 库（如 libgit2）解析 diff 需要拉整个仓库，对 PR 场景太重。

**核心数据结构**：
```cpp
struct DiffHunk {
    std::string old_file;
    std::string new_file;
    int old_start, old_count;     // -区域
    int new_start, new_count;     // +区域
    std::vector<DiffLine> lines;  // 每行的类型(ADD/DEL/CTX)和内容
};

struct DiffLine {
    enum Type { ADD, DEL, CTX } type;
    std::string content;
};
```

**解析策略**：从 GitHub API 获取的 patch 字段直接按 `@@ ... @@` 分割，逐行分类。约 200 行代码即可覆盖 95% 场景。

### 4.2 AST Analyzer（libclang 集成）⭐ C++ 核心差异化

**这是 C++ 做 PR Review 工具的不可替代优势**——Python/Node 生态的 AST 工具对 C++ 代码支持极差，而 libclang 是 Clang 官方 C API，能完整解析 C/C++ 模板、宏、继承。

**提取信息**：
- 变更函数的**调用者列表**（谁调了这个函数）
- 变更函数的**被调用列表**（这个函数调了谁）
- **继承关系**（override 的虚函数、基类实现）
- **类型别名 / typedef 链**

**实现**：
```cpp
class ASTAnalyzer {
public:
    explicit ASTAnalyzer(const std::string& compile_commands_path);
    
    struct CallGraph {
        std::string function_name;
        std::string file_path;
        int line;
        std::vector<std::string> callers;   // 谁调了我
        std::vector<std::string> callees;   // 我调了谁
    };
    
    // 对 diff 中涉及的文件做增量分析
    std::vector<CallGraph> analyze(const std::vector<DiffHunk>& hunks);
    
private:
    CXIndex index_;
    std::string compile_db_path_;
    
    // libclang visitor 回调
    static CXChildVisitResult visitCallExpr(CXCursor cursor, CXCursor parent, void* data);
    static CXChildVisitResult visitCXXMethodDecl(CXCursor cursor, CXCursor parent, void* data);
};
```

**compile_commands.json**：从 PR 的 CI 配置（Makefile/CMakeLists.txt）推断编译选项，或使用 `-fsyntax-only` 宽松模式（只做语法分析不生成目标文件）。

### 4.3 Context Assembler

**目标**：把 diff + AST + 规则匹配结果组装成 ≤ 4K token 的上下文，塞进 Prompt。

**组装策略**：
```
[系统角色定义]                    ~200 token
[PR 元信息: 标题/描述/标签]       ~100 token
[变更摘要: 文件列表+行数统计]     ~200 token
[逐文件: diff + AST调用链摘要]    ~3000 token (核心)
[规则引擎命中结果]                ~300 token
[输出格式要求]                    ~200 token
```

**规则引擎**（硬编码，不依赖 LLM）：
- 新增 `malloc`/`new` 未配对 `free`/`delete` → 🔴
- 修改虚函数/接口 → 🔴
- 纯格式化变更（只改空格/换行） → 🟢
- 修改测试文件 → 🟢
- 新增 TODO/FIXME → 🟡

### 4.4 Multi-Agent Pipeline

三个 Agent 共享同一个 LLM 后端，但使用不同的 System Prompt 和 Few-Shot 示例：

**Summarize Agent**：
- 输入：完整上下文
- 输出：JSON `{ summary: string, intent: string, affected_areas: string[] }`
- 模型：轻量模型即可（DeepSeek-V3 / Qwen2.5-7B）

**Risk Detect Agent**：
- 输入：完整上下文 + Summarize 结果
- 输出：JSON `{ risks: [{ file, line, level, reason, suggestion }] }`
- 模型：需要代码理解能力强的模型（DeepSeek-V3 / Qwen2.5-Coder-32B）

**Critic Agent**：
- 输入：Risk Detect 结果 + 原始 diff
- 任务：逐条验证风险项，标记「确认/误报/待定」
- 输出：JSON `{ verified_risks: [...], filtered: [...] }`
- 模型：同 Risk Detect（自洽校验）

**流水线并发**：Summarize 和 Risk Detect 可以并行（后者独立看 diff 也能识别明显风险），Critic 必须等 Risk Detect 完成。实际执行是 **Summarize ‖ Risk Detect → Critic**。

### 4.5 LLM Gateway（流式 + 重试 + 缓存）

```cpp
class LLMGateway {
public:
    struct Config {
        std::string api_base;     // "https://api.deepseek.com/v1"
        std::string model;
        std::string api_key;
        int max_retries = 3;
        int timeout_ms = 30000;
    };
    
    // 流式调用，回调逐 token
    using StreamCallback = std::function<void(const std::string& token)>;
    Future<std::string> chat(const std::string& system_prompt,
                             const std::string& user_prompt,
                             StreamCallback cb);
    
private:
    Config config_;
    // SQLite 缓存: prompt_hash → response
    std::unique_ptr<Cache> cache_;
    // 连接池: 复用 HTTP 连接
    std::unique_ptr<ConnectionPool> pool_;
};
```

**流式输出**：SSE 解析（cpp-httplib 原生支持），首 token < 3s，边生成边写终端。

**缓存**：同一 PR + 同一 diff 的分析结果缓存在本地 SQLite，避免重复调用。

## 五、关键技术决策

### 5.1 模型选择

| 候选模型 | 优势 | 劣势 | 决策 |
|---------|------|------|------|
| DeepSeek-V3 | 代码理解强、中文好、$0.27/M token | 需联网 | **主选** |
| Qwen2.5-Coder-32B | 可本地部署、开源 | 32B 显存需求高 | 本地备选 |
| GPT-4o | 最强 | 贵（$2.5/M）、国内不稳定 | 不选 |

**路由策略**：
- Summarize Agent → DeepSeek-V3（轻量任务用便宜模型即可）
- Risk Detect + Critic → DeepSeek-V3（同一模型保证自洽性）

### 5.2 上下文获取方式

| 方式 | 实现难度 | 信息量 | 选择 |
|------|---------|--------|------|
| GitHub API 拉 diff | 低 | diff 内容 | ✅ 必须 |
| libclang AST 分析 | 高 | 调用链/继承 | ✅ C++ 差异化核心 |
| Git blame 历史分析 | 中 | 最近修改者/频率 | ⏳ 未来扩展 |
| Embedding 检索相似 PR | 高 | 项目级知识 | ⏳ 未来扩展 |

**MVP 上下文**：diff + AST 调用链 + 规则引擎命中结果，控制在 4K token 以内。

### 5.3 为什么用 C++ 而不是 Python

这是面试/路演必问的，答案不是「C++ 更快」这么简单：

1. **libclang 是 C API**：C++ 可以零开销直接调用，Python 的 python-clang 绑定有内存管理坑、类型信息丢失
2. **AST 分析是 CPU 密集型**：大项目（Chromium 级别）的 AST 解析，C++ 比 Python 快 10–50 倍
3. **线程池 + 协程调度**：Multi-Agent 并发 + 流式输出 + 连接池复用，C++ 的内存模型和调度精度远优于 Python GIL
4. **面试加分**：C++ 做 LLM 工具是差异化，能展示你对「语言选型」有思考，不是无脑 Python

**但**：C++ 不适合做 LLM 应用全栈——我们只做「调度层 + AST 层」，LLM 调用走 HTTP API，不硬扛。

### 第三方依赖

### 不用 Boost 的理由

1. 编译慢、体积大，3 天交付时间耗不起
2. cpp-httplib + nlohmann/json 已覆盖 HTTP + JSON，无需 Boost.Beast / Boost.PropertyTree
3. 面试官问起来，你能说出「按需选型，不为了用而用」比「全上 Boost」更成熟

## 七、评测方案

> 这是大多数参赛者不会做的——**自建评测集 + 量化指标**，路演拿出来直接赢一半。

### 评测集

从公开仓库收集 15–20 个真实 PR，人工标注：
- 每个文件的风险等级（高/中/低）
- 每个真正存在的问题（bug/安全/性能/风格）

### 指标

| 指标 | 定义 | 目标 |
|------|------|------|
| **召回率** | 真实问题中被系统识别出的比例 | ≥ 60% |
| **误报率** | 系统标记的问题中实际不是问题的比例 | ≤ 30% |
| **风险分级准确率** | 文件风险等级与人工标注一致的比例 | ≥ 70% |
| **首 token 延迟** | 从发起请求到首个 token 返回 | < 3s |
| **完整报告延迟** | 从发起请求到完整报告生成 | < 30s |

### 消融实验

| 配置 | 说明 |
|------|------|
| 仅 LLM（无 AST） | 验证 AST 上下文的增益 |
| 仅规则引擎 | 验证 LLM 的增益 |
| 无 Critic Agent | 验证交叉校验对误报率的改善 |
| 完整系统 | 基线 |

## 九、路演金句（5 分钟版）

1. **「libclang 是 C++ 的母语」** — Python/Node 的 AST 工具对 C++ 代码支持极差，我们直接用 Clang 官方 API，模板、宏、继承全解析。
2. **「Critic Agent 把误报率压下去」** — 不只是让 LLM 找问题，还让另一个 LLM 校验结果，像 Code Review 的 Review 一样。
3. **「3 个 Agent 并发跑，30 秒出报告」** — C++ 协程 + 线程池 + 流式输出，不是等 3 分钟才出一坨 JSON。
